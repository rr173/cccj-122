# 事实仓灾备：一致备份、增量块存储、离线恢复与保留清理

为 SQLite 事实仓（`xbrl_ingest` 的库）提供**可重复演练**的灾备能力：
生产接入还在运行时取出一份一致的独立数据库映像，按内容摘要复用地保存
各备份之间变化的文件块；生产库和原始 XBRL 都移走后，仍能只凭备份目录
恢复出当时完整、可查询的事实仓。

本模块只处理整个事实库的存储：不筛选业务行，不向接收方发送分片，不重做
事实接入或合计核查；不修改已有事实表，也不在源库中新增任何内部表。

```bash
cd batch_export
python3 demo/run_backup_drill.py     # 完整灾备演练（163 项检查）
python3 -m unittest discover -v      # 169 个测试（含 40 个本模块测试）
```

## 1. 命令

```bash
# 创建：第一次不指定父备份，是完整根；之后可显式指定同目录内某份备份为父
python3 -m warehouse_backup.cli create  BACKUP_DIR --db WAREHOUSE.sqlite [--parent N]

# 查看：列出全部备份 / 某备份的清单与逐层块来源
python3 -m warehouse_backup.cli list    BACKUP_DIR
python3 -m warehouse_backup.cli show    BACKUP_DIR --id N

# 检查：严格校验清单、父链与每个被引用块的长度+摘要，并拼出完整映像比对摘要
python3 -m warehouse_backup.cli check   BACKUP_DIR [--id N]

# 恢复：把编号 N 的备份组装到离线目标路径（默认拒绝覆盖已有目标）
python3 -m warehouse_backup.cli restore BACKUP_DIR --id N --target OUT.sqlite [--replace]

# 保留：先预览（默认），确认后加 --apply 才真正删除
python3 -m warehouse_backup.cli prune   BACKUP_DIR --keep N [--keep M ...] [--apply]
```

所有命令支持 `--json`。退出码区分三类失败，便于脚本分辨：

| 退出码 | 含义 | 例子 |
|---|---|---|
| 0 | 成功 | |
| 2 | 调用/输入错误 | 未知备份编号、源库不存在、目标已存在而未给 `--replace`、未知 `--keep` 编号 |
| 3 | 备份仓损坏 | 清单字段非法、缺父清单、父链成环、块缺失/损坏、符号链接替换、映像摘要不符、SQLite 完整性检查失败 |
| 4 | 目标写出失败 | 暂存文件创建/写入/fsync/最终改名失败（如目标目录不存在） |

失败信息分别以 `invocation error:` / `corruption error:` /
`target-write error:` 开头打印到 stderr。

## 2. 备份目录格式（格式版本 1）

```
BACKUP_DIR/
  FORMAT                  # 固定内容 "warehouse-backup/1\n"，不符即拒绝
  lock                    # flock(2) 协调文件，永不删除
  manifests/000001.json   # 每份备份一份清单，先在 tmp/ 写全再原子改名公布
  chunks/hh/<64hex>.chunk # 按内容摘要寻址的块文件（前 2 位十六进制分目录）
  tmp/                    # 暂存区：创建中的映像与未公布清单；永不被当作备份
```

清单是严格校验的 JSON 对象，字段**恰好**为：

```json
{
  "format": 1,
  "id": 3,
  "parent": 2,                  // 根为 null
  "created_at": "2026-11-14T12:00:00.000+00:00",
  "image_size": 147456,         // 完整映像字节数
  "image_sha256": "<64 hex>",   // 完整映像摘要
  "chunk_size": 65536,          // 必须等于固定块长
  "chunk_count": 3,             // 必须等于 ceil(image_size/65536)
  "chunks": [                   // 只登记本层自己存的块
    {"index": 1, "length": 65536, "sha256": "<64 hex>"},
    {"index": 2, "length": 16384, "sha256": "<64 hex>"}
  ]
}
```

校验拒绝：未知或多出的字段、缺字段、格式版本不符、id 与文件名不符、
父编号为自身、非 64 位小写十六进制摘要、`chunk_size` 不等于 65536、
`chunk_count` 与 `image_size` 不符、块序号越界或不递增、块长度与该序号
应有长度不符（中间块必须 65536，尾块为剩余长度）。

**块来源规则（怎样从父链决定某块来自哪一层）**：恢复编号 N 时，沿
`N → parent → … → 根` 依次查找，块 `i` 取自**最靠近 N 的、清单中登记了
`i` 的那一层**。子清单登记的是与父映像逐块比对后**发生变化**的块，以及
超出父 `chunk_count` 的新块；未变块沿父链继承。序号 ≥ 本备份
`chunk_count` 的块从不被查询——所以库收缩后，父映像多出的尾部和旧尾块
绝不会被带回子备份的恢复结果。`show --id N` 会打印每个块区间实际来自
哪一层。

**共享与去重**：块文件以内容摘要命名，多份清单（包括不同分支）引用同一
摘要时磁盘上只有一份；再次备份同样内容会产生新编号，但共享块不再写一份
（`create` 输出里 `reused_chunk_files` 计数）。

**路径安全**：备份编号是整数、块名是校验过的 64 位十六进制，所有路径都
由程序在备份目录内拼出，清单内容无法变成越界路径。目录内任何位置出现
符号链接或非常规文件即视为仓损坏（退出码 3），绝不跟随。

## 3. 一致备份的取得（对正在使用的库）

`create` 用 SQLite 在线备份 API（`sqlite3.Connection.backup`）复制源库：

* 源库可以是 WAL 模式、可以有其他连接持续写入；**不要求**调用方停写或
  先做 checkpoint；
* 映像始终对应**某个完整提交**的状态，不会混合两个事务的表内容；
* 备份后源库连接与业务写入照常可用（演练第 1、7 阶段实际验证）；
* 映像落盘前把日志模式翻转为 rollback（`PRAGMA journal_mode=DELETE`），
  使保存的映像自包含、可只读打开，不依赖任何 `-wal`/`-shm` 侧车文件。

映像切成 65536 字节定长块（最后一块可较短）。整个 `create` 持有排他锁，
与恢复、检查、清理互斥协调。创建用的临时映像写在 `tmp/`，清单公布后
立即删除，**不参与**任何恢复。

---

## 4. 离线恢复的前提与保证

恢复只需要：**备份目录** + **一个离线目标路径**。源数据库、原始 XBRL
实例文件、创建时的临时映像都不参与恢复（演练第 5 阶段把它们全部移走后
恢复）。目标必须位于备份目录之外。

恢复过程：逐层解析父链 → 按序号顺序组装到目标旁的私有暂存文件 → 逐块
校验长度与摘要 → 校验完整映像的字节数与摘要 → 用 SQLite 自己的
`PRAGMA integrity_check` 检查 → 再次核对映像摘要 → 原子改名到目标。

* 目标已存在时默认拒绝（退出码 2）；`--replace` 下任何校验或写入失败都
  保住原目标字节不变（演练第 8 阶段验证）；
* 绝不修改备份内容来"修复"损坏，也绝不退到某份较旧备份却声称恢复了
  指定编号：链上缺父、成环、块损坏都直接以退出码 3 失败；
* 恢复出的库能用仓库原有入口（`xbrl_ingest` 的 `query`/`search`/
  `trace`/`sources` 及 CLI）直接打开；数值文本、nil、冲突候选与全部
  来源关系原样保留（演练第 5 阶段用与生产库完全一致的业务快照比对）。

`check` 与 `restore` 的区别：`check` 验证仓内清单与块（含拼出完整映像
比对摘要），不产出文件；`restore` 在此之上额外运行 SQLite 完整性检查并
交出数据库文件。

## 5. 保留清理（先预览，再应用）

```bash
python3 -m warehouse_backup.cli prune BACKUP_DIR --keep 3 --keep 4          # 预览
python3 -m warehouse_backup.cli prune BACKUP_DIR --keep 3 --keep 4 --apply  # 应用
```

* 程序先说明：哪些清单是保留项父链上的**必要依赖**（即使不在保留列表中
  也不删）、哪些清单与块可以释放、其中哪些块已无任何清单引用（失败创建
  留下的孤儿块）、释放字节数；
* 被多个分支共用的块，只要任一保留链还需要就留下；
* 未正式公布的清单（`tmp/` 里的暂存）不被当作可恢复备份，失败留下的
  无引用块会被后续清理识别回收；
* 应用时在排他锁内**重新计算**保留集（不轻信预览），先删清单再删块：
  中途崩溃只会留下可被下次清理识别的孤儿块，不会留下指向已删块的清单；
* 遇到缺失父清单、父链成环、坏字段或坏引用（含被引用块缺失/损坏）时，
  预览与应用都拒绝（退出码 3），不猜一个保留集合继续删；
* 锁协调：恢复/检查持共享锁，清理应用持排他锁——已经开始读取依赖的
  恢复不会被另一进程的清理抢先删掉正要读的文件（演练第 10 阶段用
  `--pause-gate` 实际验证）。

## 6. 演练各阶段的运行方式

`python3 demo/run_backup_drill.py` 在临时目录里完整走一遍，退出码 0 表示
全部检查成立。各阶段对应的能力：

| 阶段 | 内容 |
|---|---|
| 0 | 建生产库（WAL + 基线数据表），接入 demo-A/B，列出并核对预期来源与事实（同值重复、冲突、nil、高精度数） |
| 1 | 接入连接保持打开时创建根备份；备份后生产仍是 WAL、接入继续可用 |
| 2 | 接入 demo-C 建子备份、接入 demo-D 建孙备份，再从根分出另一支；核对块复用与 `show` 的逐层来源 |
| 3 | 辅助表把映像撑大后 DELETE+VACUUM 缩小；增量恢复的字节数与独立摘要精确相等，无旧尾部 |
| 4 | 同样内容再备份：新编号、零新块文件 |
| 5 | 把生产库与原始 XBRL 移走；离线恢复三层链与分支，用独立整文件摘要 + 原业务查询快照比对 |
| 6 | 保留孙备份与另一分支的预览/应用；必要祖先与共享块保留，恢复仍可用 |
| 7 | WAL 写进程持续提交（一个事务同时推进两个表的标记），备份恢复后两标记相等 |
| 8 | 共享块损坏/缺失：检查与恢复退出码 3，已有目标字节不变，不留半成品 |
| 9 | 缺父、父链成环、坏字段、越界块引用：预览与应用均退出码 3 且什么都没删 |
| 10 | 进程间同步让恢复停在已取得依赖之后，证明清理不会抢先删除它要读的文件 |
| 11 | 块/清单被符号链接替换：检查与恢复拒绝 |
| 12 | 退出码分类（2/3/4），原有接入/查询 CLI 在恢复库上可用，完整测试套件通过 |

单独复跑某个场景时，可直接用第 1 节的命令在任意目录操作；`--pause-gate`
是演练/测试专用钩子（恢复取得依赖后先写 `<gate>.acquired` 再等待
`<gate>.go` 出现），正常业务路径不需要。

## 7. 代码结构

```
warehouse_backup/
  errors.py    # 错误类型与退出码（2 输入 / 3 损坏 / 4 写出）
  format.py    # 格式版本、清单模型与严格校验、块长常量 65536
  store.py     # 目录布局、flock 协调、清单/块的原子读写、符号链接拒绝
  service.py   # 创建（在线备份 API）、检查、恢复、保留预览/应用
  cli.py       # 终端命令
tests/test_warehouse_backup.py   # 40 个测试（含 WAL 一致性与锁协调子进程）
demo/run_backup_drill.py         # 可重复灾备演练（163 项检查）
```

## 8. 与既有模块的关系

`warehouse_backup` 不导入、不修改 `xbrl_ingest`、`export_delivery`、
`calc_check`；它只把事实仓的 SQLite 文件当作整体存储来备份与恢复。
恢复出的库由 `xbrl_ingest` 的既有入口打开查询；导出交付与计算核查命令
不受影响（演练第 12 阶段跑完整测试套件证明）。
